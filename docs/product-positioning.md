# Product positioning

## The business problem

Knowledge workers receive information in project folders, PDFs, spreadsheets,
presentations, and web sources. Existing AI tools can summarize or generate a
document, but they often fail at the business-critical middle: showing what
was used, coordinating specialist work, producing editable output, and asking
for approval before a consequential action.

## The product promise

DSH Work helps a person turn project sources into a reviewable deliverable.
The product should make the work visible enough that a manager, analyst, or
client can approve it without trusting an opaque autonomous process.

## Target user

The first target user is a professional who repeatedly prepares reports,
analysis spreadsheets, and presentations from mixed source material. Typical
examples include strategy teams, analysts, researchers, operations teams, and
consultants.

## Product boundary

| Category | DSH Work position |
| --- | --- |
| AI chat | A conversation is one interface, not the product output |
| Office editor | DSH Work creates and reviews editable files; it does not initially replace Office editors |
| Generic cowork app | DSH Work focuses on document-centered knowledge work |
| Automation platform | External automation follows local review and approval capability |
| DSH distribution | DSH Work is an office-oriented product layer, not only a desktop wrapper |

## Differentiation to earn

The differentiation is not a larger tool catalog. It is a reliable chain from
source to deliverable:

1. Sources remain attached to the project.
2. Roles have bounded permissions and responsibilities.
3. Generated claims can be reviewed against evidence.
4. Editable files remain first-class work objects.
5. Significant actions wait for a human decision.

This is how DSH's profiles, presets, plugins, workflows, and approvals become
a business product rather than developer configuration terminology.
