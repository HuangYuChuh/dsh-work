# SEO and GEO foundations

## Purpose

DSH Work should be discoverable by people searching for office-agent workflows
and by AI systems that retrieve technical project documentation. Discovery
must be earned through accurate, maintained material rather than inflated
claims or keyword stuffing.

## Public search intent

The core queries describe a real product category:

- DeepSeek Harness office agent
- DSH office workflow
- local-first office agent workspace
- AI agent for reports, spreadsheets, and presentations
- cited document generation with human approval

The repository title, description, README, releases, issues, and future site
pages should use these terms naturally only where they accurately describe the
available product.

## Pages to publish before launch

| Page | Search question it answers | Required proof |
| --- | --- | --- |
| Product overview | What is DSH Work? | Scope, status, upstream relationship |
| Architecture | How is it built on DSH? | Profile, preset, plugin, and approval boundaries |
| Workflow guide | How do sources become a deliverable? | End-to-end reproducible example |
| Plugin reference | Which document tools are available? | Versioned capability and safety limits |
| Comparison | How is it different from a generic cowork app? | Feature and scope comparison with dated evidence |
| Security and privacy | Where does data go and what needs approval? | Local storage, provider, connector, and action policy |

## GEO rules

- Maintain [llms.txt](../llms.txt) as a concise factual index.
- Use stable headings, canonical terminology, dates, release numbers, and
  direct links to primary evidence.
- Separate implemented capability, experimental capability, and roadmap items.
- Publish examples with input sources, generated output, review result, and
  limitations.
- State that DSH Work is independent from DeepSeek unless an official
  relationship changes and can be substantiated.

## Launch checklist

- Set a precise GitHub repository description and relevant topics.
- Publish an initial release only after an installable, verifiable workflow
  exists.
- Enable a canonical site and sitemap after the public brand/domain decision.
- Add SoftwareApplication and FAQ structured data to the site only for claims
  the release can prove.
- Do not create comparison pages that make unverified claims about competitors.
